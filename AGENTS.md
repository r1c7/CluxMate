# Project memory

## What CluxMate is

- CluxMate = one Python agent core (`cluxmate/`) driving three front-ends: headless CLI (`cluxmate -p "..."`), Textual TUI (`cluxmate`), and an Electron desktop (`desktop/`) that drives the core over JSON-RPC stdio (`cluxmate agent stdio`). Providers are OpenAI-compatible only (`core/providers/` = base + openai + factory; no Anthropic provider).
- Four risk modes (`plan` / `default` / `acceptEdits` / `yolo`): `plan` registers only read tools (no bash/write/delete/task/update_memory/MCP — hard isolation, nothing to approve); `default` approves `safe` automatically, asks for `write`/`dangerous`; `acceptEdits` auto-approves `write`; `yolo` disarms the sandbox boundaries entirely (the one explicit opt-out). Mode is per-session only, never persisted. Risk levels are `safe` < `write` < `dangerous` < `critical`; `critical` (bash `format`/`mkfs`/`dd`/`> /dev/`/`chmod 777`) never auto-approves and is never always-allowable, like escalation. Running code (interpreters/build tools/scripts — `python`, `node`, `npm run`, `./x.sh`, …) is `dangerous` (never `safe`), classified by runner name with a `run` fallback for unlisted executables. Permissions.json stores two always-allow tiers: `always_allow_tools` (write risk) and `always_allow_dangerous_tools` (dangerous risk — `delete_file` whole-tool, and `bash` PER category `"bash:rm"`/`"bash:git-reset-hard"`/`"bash:python"`/`"bash:run"`/…, never a bare `"bash"`; escalation `danger-full-access`, `critical` bash, and MCP dangerous tools are never always-allowable).
- The repo root IS a git repo (`.git/`, branch `master`, remote `git@github.com:r1c7/CluxMate.git`, init 2026-08-25, actively committed since). `.gitignore` excludes `docs/`, `scripts/`, `.cluxmate/`; `snapshots/*.png` (UI screenshots) ARE tracked. Checkpoint shadow-git repos live separately in `~/.cluxmate/checkpoints/<sha1(cwd)>.git` (see `core/checkpoints.py`) and never touch the user's real repo (GIT_DIR/GIT_WORK_TREE set via env + `GIT_CONFIG_GLOBAL=/dev/null`).

## Architecture — core invariants

- The session log is **event-sourced and the source of truth** (`cluxmate/core/session_log.py` docstring): provider message history is *derived* from the append-only log, never stored separately. Model-visible request == `[system from fold_request_header] + derive_messages()`; `derive_messages()` deliberately excludes the system prompt. `request/header` events record the full non-history envelope (config incl. model/max_tokens/context_window/mode/sandbox/reasoning_effort + system prompt + tool schemas) with reason `initial`/`change`; only changed headers are appended (`header_equals`/`canonical_header` in `core/agent.py`). `config.sandbox` is the effective shell-sandbox state (`off`/`bwrap`/`seatbelt`/`windows-lowil`/`fail-closed`) — audit metadata, NOT model-visible (the model learns the boundary only empirically from denials). Compaction rewrites a *surface* projection via `replace` ops without erasing the underlying events, preserving a cache-stable prefix. `tool/result` events carry non-surface audit fields alongside `message` — `riskLevel`, `categories`, `decision` (`auto`/`user`/`always`/`denied`), `escalated` — recording the permission request/response without entering the model-visible surface.
- Environment context — memory, skills, mode — is injected as **tagged synthetic `user/message` events** (`source: memory` / `skill` / `mode`; also `human`, `compaction`, `interruption`), NOT baked into the system prompt, so request prefixes stay prompt-cache stable. A mode or tool-schema change appends a fresh `request/header` with reason `change`.
- `AgentBuilder` (fluent, `core/builder.py`) is the single wiring point: it registers tools, the WriteFence, the bash/MCP sandbox, and subagent types. A `chat/set_mode` change rebuilds the agent so a mode switch re-arms/disarms sandbox boundaries.
- Subagents are child `SessionLog`s linked to the parent via `subagent/spawn` events; replay walks the whole delegation tree depth-first (`session_log_store.py`). Recursion capped at `MAX_SUBAGENT_DEPTH = 4` (root = depth 0); at the cap the `task` tool is withheld. `general-purpose` children may recurse to either type; `explore` children recurse only within `explore` (TaskTool allowlist keeps the chain read-only).
- Torn session tails are dropped on load; an interrupted turn is closed with synthetic `tool/result` + `turn/end {interrupted}` (crash-repair closers, dropped when premature); undo rewinds to a turn boundary via a single `truncate`.
- **Completion audit (anti-fake-completion, shipped 2026-09)** — `core/completion_audit.py` reconciles every `end_turn` reply against the turn's executed tool calls (claim-vs-evidence, modeled on Reasonix's receipt-ledger `AdjudicateCompletion` / grok's `stalled_false_completion` / pi's record-log validation). The loop records executed write paths + bash calls per turn (`agent.py`, denied/malformed/errored calls don't count) and, before committing a final reply, bounces unsupported claims back to the model ONCE as a synthetic `source:"completion-audit"` user message (`MAX_COMPLETION_AUDIT_RETRIES = 1`; advisory, never hard-blocks). Detects: file-change claims with no write-tool calls / paths the writes didn't touch; test/command-outcome claims with no bash call. **Bash turns get a filesystem fallback (B-lite)**: when a bash call ran, the tool record can't say WHAT changed, so claimed files are checked against the filesystem — `resolve_file_touched(name, cwd, turn_start_ts)` stats the claimed path / walks the workspace for the basename (skips `.git`/`node_modules`/venv/…, bounded `_SCAN_FILE_BUDGET`; unknown ⇒ skip, never bounce) and `mtime >= turn start` verifies the claim; `AgentLoop(cwd=…)` (wired by `builder.py`) supplies the resolver — without a cwd the bash branch keeps the conservative v1 skip. Deletion claims are skipped (a deleted file looks like one that never existed); no bash command-semantics matching yet (Reasonix `commandmatch.go` territory). Negated claims ("did not fix") are skipped; a bare "done" with no file/test token never fires. `turn/end.reason.completion_audit = {reminders: N}` records bounces. Prompt side: `system_prompt.j2` `<completion_protocol>` (evidence before claim, run cheapest verification before claiming, quotes required) and `child_system_prompt.j2` requires a `**Status**: success|partial|failed|blocked` header + evidence rule; `tools/task.py` wraps a child result whose last `turn/end` kind is aborted/interrupted/max-turns/max-tokens/error with an explicit "did not complete normally" prefix (run-settlement whitelist pattern) and mirrors `session_log_store.py`'s done/error classification for the live `agent_end` tree event. Pure logic unit-tested in `tests/core/test_completion_audit.py` (30 tests).

## Security: sandbox (READ the docs before touching this code)

Two enforcement boundaries sit behind the permissions policy (`core/permissions.py` decides what is *allowed*; the boundaries make denials stick). Authoritative Chinese docs: `docs/plans/sandbox-current-state.md` (current implementation) and `sandbox-threat-model.md` (decisions/threat model). Read them before touching `tools/_fence.py` / `tools/_sandbox.py` / `core/grants.py`.

- **WriteFence (T1, in-process)** — guards the 5 file tools `write_file` / `search_replace` / `multi_edit` / `multi_write` / `delete_file` (batch tools check each item; out-of-bounds items are skipped). Canonicalize-then-contain: `resolve(strict=False)` (resolves `..` and symlinks) → deny check → contain check, before any I/O.
  - Writable roots defined in exactly one place: `WriteFence.roots()` = session cwd + platform temp dir + exactly `~/.cluxmate/AGENTS.md` (whitelisted so `update_memory`'s "edit global entries with search_replace" contract works) + user-granted folders. The rest of `~/.cluxmate` (config.json with API keys, session logs, checkpoints) is off-limits.
  - `<cwd>/.cluxmate/` is a **deny subtree** (takes precedence over roots): it holds CluxMate's privileged project state (permissions.json always-allow, mcp.json which spawns subprocesses on load, skills.json) — a prompt-injected model must not edit its own permission config. Deny-subtree rejections are NOT openable by escalation.
  - Enabled in all modes except `yolo`.
- **Bash + MCP stdio sandbox (T2, OS-level)** — glue over OS primitives, nothing from scratch: Linux = bubblewrap (bwrap) mount namespaces (root fs read-only, temp then workspace bind-mounted writable, `<cwd>/.cluxmate` re-mounted read-only LAST so it overrides the writable binds, minimal /dev + fresh /proc, `--die-with-parent`; network stays SHARED — documented omission); macOS = Seatbelt via `sandbox-exec` (`(allow default)` minus writes — denied everywhere except workspace/temp/granted folders; `<cwd>/.cluxmate` re-denied; reads/network unrestricted); Windows = Low integrity-level token with `NO_WRITE_UP`, workspace tree labeled low-IL via icacls (marker-cached in `<cwd>/.cluxmate/sandbox-il-applied`), `<cwd>/.cluxmate` deliberately re-labeled medium so the sandboxed shell can't edit permission config, `<cwd>/.cluxmate/tmp-low` labeled low as the child's TMP/TEMP. Low-IL can still READ everything and reach the network — enforcement is partial by design (`enforcement="partial"` on every backend).
  - **Fail-closed**: sandbox enabled + no backend available → BashTool refuses to run (never falls back to bare subprocess). Escape hatch: `CLUXMATE_BASH_SANDBOX=off` (explicit, env-scoped). The backend is chosen once when tools are built (`pick_sandbox` probes availability; Windows requires `icacls` on PATH) — changing the env var mid-process does nothing.
  - Windows shell nuance: real Git Bash (MSYS2) is preferred when on PATH and working, but it CANNOT run under the Low-IL sandbox (runtime NtCreateDirectoryObject 0xC0000022), so BashTool falls back to the cmd.exe `shell_cmd` path; WSL's bash.exe is never the default (Linux-side DrvFS/interop escape the integrity boundary).
  - **Per-call escalation**: mutating tools accept `sandbox_permissions="danger-full-access"` + one-sentence `justification` (paired; validated at execution by `validate_escalation_args`). Requesting it raises the call's risk to `dangerous` so the existing approval prompt fires BEFORE execution; an approval grants the wider mode for that ONE call (file tools skip fence containment, bash runs unsandboxed).
- `core/grants.py` = the always-allow **writable-folder registry** at `~/.cluxmate/sandbox-grants.json` (user-global, one per user — NOT per-project). `dangerous` commands prompt unless explicitly always-allowed (`always_allow_dangerous_tools` — `delete_file` whole-tool, or `bash:<category>` per destructive/code-runner category, never a bare `"bash"`); `critical` commands (bash `format`/`mkfs`/`dd`/`> /dev/`/`chmod 777`) and sandbox escalation (`danger-full-access`) always prompt outside `yolo`.
- **Read denylist + built-in sensitive-file template** (shipped 2026-09-03, the P0 "敏感文件读保护默认值"): `~/.cluxmate/forbid-read.json` = `{"protect_sensitive": bool, "paths": [...]}` (`core/read_denies.py`, user-global; legacy paths-only files load with toggle off). `protect_sensitive` is a one-click opt-in (default OFF = zero behavior change, mirrors Reasonix `[secrets] protect_sensitive_files`): pattern rules `.env`/`.git-credentials`/`.netrc` (exact basename) + `*.pem`/`*.key`/`*.p12`/`*.pfx` (suffix, case-insensitive) enforced ONLY at the process level by `ReadFence` (read_file/grep/list_dir, all platforms); fixed dirs `~/.ssh`/`~/.aws` + `~/.gnupg` (POSIX)/`%APPDATA%\gnupg` (Windows) join `effective_paths()` so bwrap/Seatbelt can also enforce them (Windows Low-IL read side stays documented no-op). Builder wires `_read_deny_paths()` (effective) into ReadFence + `pick_sandbox(deny_read_paths=...)` and `_protect_sensitive()` into ReadFence only. JSON-RPC `sandbox/forbid_read` get returns `{paths, protect_sensitive}`; `set` takes params dict (paths replace and/or toggle flip) + rebuilds the agent. Desktop Settings toggle + read-only template chips kill the bridge like grants.

## Hooks

Lifecycle hooks (Claude-Code-style, full 9-event surface): user-defined shell commands at `UserPromptSubmit` / `PreToolUse` / `PostToolUse` / `Stop` / `SessionStart` / `SessionEnd` / `SubagentStop` / `PreCompact` / `Notification`, receiving a JSON payload on stdin (env gets `CLUXMATE_HOOK_EVENT`; `run_event(extra=...)` merges event fields — `source`/`reason`/`subagent_id`/`subagent_type`/`task_description`/`error`/`trigger`/`custom_instructions`/`message`) and writing JSON to stdout — `{"decision":"block","reason":...}` / `{"continue":false,...}` or exit code 2 blocks; `{"hookSpecificOutput":{"additionalContext":...}}` injects context; anything else continues. Per-event semantics: `Stop` block re-runs (max 3, `MAX_STOP_BLOCK_RETRIES`, streams `text_restart`); `SessionStart` block aborts startup (JSON-RPC initialize returns an error; CLI/TUI exit/return the reason) and feedback prepends to the FIRST turn only; `SubagentStop` block replaces the subagent's reply in the parent (`tools/task.py`); `PreCompact` block skips compaction for that step, feedback enters the (pre-compaction) context; `SessionEnd`/`Notification` discard output (Notification fires auto at turn end on desktop + manual `hooks/notify` RPC / desktop "Test notify" button, on a daemon thread). `SessionEnd` fires on clean shutdown only (stdin EOF / process exit / session change / REPL `/clear`; a re-initialize with the SAME session_id fires neither SessionEnd nor SessionStart). Configured in `settings.json` (global `~/.cluxmate/` + project `<cwd>/.cluxmate/`, project runs after global). `hooks/get` / `hooks:get` JSON-RPC returns the normalized list; `reload_hooks` re-reads settings.json in place; hook runs stream as `hook_start`/`hook_result` chat events. Trust model: hooks are the user's own config, NOT sandboxed (run at normal integrity, not the Low-IL/bwrap sandbox), not model output. Authoritative doc: `docs/plans/hooks.md` (D1–D18). Read before touching `core/hooks.py` / `core/agent.py` (Stop block/retry + PreCompact) / `tools/task.py` (SubagentStop) / `core/jsonrpc_server.py` (hooks/get + hooks/notify + SessionStart/SessionEnd + hook_start/hook_result/text_restart stream events).

## SSRF guard (shipped 2026-08-30, commits 5a762f8..c89a446)

- `web_fetch`/`web_search` are guarded by an SSRF guard in ALL modes INCLUDING yolo (deliberate: it defends against remote prompt-injection, not model intent). Core: `cluxmate/tools/_ssrf.py` (`validate_url(url, allow, block_extra) -> str | None`, `parse_entry`, `SSRFBlockedError`, `DEFAULT_BLOCKED_NETS` — 17 nets incl. RFC1918/loopback/link-local/metadata/NAT64/`::/96`). Config: `cluxmate/core/ssrf_config.py` (`SsrConfig`, mtime-cached `snapshot()` so file edits take effect next request — NO bridge kill, unlike grants).
- User config `~/.cluxmate/ssrf.json` = `{"allow": [...], "block_extra": [...]}`; entries `host` / `host:port` / `[ipv6]:port` / IP / CIDR. **allow wins over every block** (incl. block_extra and the built-in table). The file is inside WriteFence's non-writable `~/.cluxmate/`, so the model can't self-allow.
- Wiring: httpx `event_hooks={"request": [...]}` re-validates EVERY hop incl. redirects; hooks MUST be `async def` (httpx>=0.28 awaits them). Hostname checks are DNS-per-IP with fail-closed on resolution failure; hostnames are IDNA-encoded before resolution; IPv4-mapped `::ffff:` and IPv4-compatible `::/96` forms are covered.

## Threading model (JSON-RPC server) + retrieval memory gotcha

- `JsonRpcServer._handle_chat_send` runs EVERY turn on its own fresh daemon thread with its own new event loop + executor (`jsonrpc_server.py` ~line 1104/1279) — never assume per-agent objects are used on the thread that built them. `initialize`/MCP-loader/`build()` can each run on different threads, so any object shared across agent rebuilds/turns must be thread-safe.
- Bug hit 2026-09-08 (desktop): `RetrievalMemory`'s in-memory sqlite FTS connection was created on the builder thread but `agent.run()→_recall()` ran on a per-turn thread → `sqlite3.ProgrammingError: objects created in a thread can only be used in that same thread`. Fixed by `sqlite3.connect(":memory:", check_same_thread=False)` + a `threading.Lock` held across `_reconcile`+`_search` in `retrieval_memory.py`; regression test `test_recall_from_other_thread_than_constructor` in `tests/core/test_retrieval_memory.py`. Rule: any `sqlite3`/`asyncio`/loop-bound resource on a shared object must be built per-thread or explicitly made cross-thread-safe (this is also why each turn resets the provider client — comment in `_handle_chat_send`).

### Retrieval memory — CJK/trigram facts (verified 2026-09-11, SQLite 3.45.3)

- `_tokenize` emits CJK **bigrams AND 3-char windows** (changed 2026-09-11, 方案 A). The trigrams are what reach the FTS index; the bigrams are kept so 2-char words and non-adjacent matches still recall (dropping them loses e.g. `缓存` in `缓存怎么实现` → regression test `test_recall_short_cjk_word_still_matches`). Before this, bigrams-only + `_score_term`'s `len(term) >= 3` guard meant **no Chinese term ever hit the FTS index** — all CJK recall fell through to the linear `needle in body` scan. Hard constraint: FTS5 trigram `MATCH` needs **≥3 chars** (measured: `缓存索`→1 hit, `缓存`→0, `沙`→0), so any future CJK tokenizer work must emit ≥3-char terms to use the index.
- `tokenize='unicode61'` on raw CJK is useless (a whole CJK run = ONE token → 0 hits); it works only when **both** index text and query are bigram-ized (space-separated) — `MATCH '缓存索引'` against a bigram index gives 0 hits, `'缓存 索引'` gives 1, BM25 ordering correct.
- **Correction**: `bm25()`/`rank` **DO work** under trigram (3.45.3 gave correct relevance order). Any "trigram 不支持 bm25 / rank 恒为 NULL" claim is wrong. An FTS5 table has exactly ONE tokenizer → trigram + word/BIGRAM indexes need **two virtual tables** (fuse via RRF).

Desktop `ask_user_question` — three ways a question could strand a turn (found by probe + fixed 2026-09-12; regression tests `tests/core/test_jsonrpc_question.py`, 5 tests). (1) **Renderer (the everyday one)**: the `tool_result` handler in `desktop/src/renderer/stores/index.ts` (both the sendMessage and retry event handlers) cleared `pendingQuestion` on ANY root tool_result, but the agent loop executes one step's tool calls concurrently (`asyncio.gather`) and `ask_question` is awaited inside `_execute_one` — so a sibling call settling in the same batch dismissed a still-unanswered card. Symptom: the card flashes and vanishes, `isStreaming` stays true so the composer only offers Stop, and the Python turn blocks forever on `evt.wait()`. Fix: clear only when `css.pendingQuestion?.call_id === event.call_id`. (`pendingPermission`/`pendingBatchEdit` never had this bug — `on_tool_start` is awaited sequentially in the loop, so prompts are inherently serialized.) (2) **jsonrpc_server.ask_question emitted the `question` event BEFORE registering the `threading.Event`**, so an answer landing in that tiny window was stored in `_question_answers` and never consumed; fix = register the waiter first. (3) **Two `ask_user_question` calls in one batch**: both emitted, but every front-end renders ONE card (desktop keeps a single `pendingQuestion` slot), so the second overwrote the first and stranded it; fix = a lazily-created `asyncio.Lock` in `JsonRpcCallbacks` serializing batches (re-created per turn, so it binds to that turn's loop; `cancel()` still releases it via the `_cancelled` re-check after acquiring). Diagnostic gotcha: an unanswered question parks a default-executor thread inside `evt.wait()` and `asyncio.run()`'s `shutdown_default_executor()` joins it — any script/test that abandons a waiter hangs at interpreter exit (always `cbs.cancel()` in teardown), and piped stdout buffers the prints until then, so it looks like a silent freeze.

## Compaction: balanced cuts + generation guard (P0-3/P0-4, shipped 2026-09-12)

- `core/context.py` cuts are now **tool-pairing balanced** (`_unanswered_delta` → `_balance_prefix` → `_snap_forward` / `_pairing_cut`; DSH `tool-pairing.ts` `eventDelta`/`cutBalanced`, Grok `select.rs`). `balance[i]` = unanswered tool calls immediately before message `i`; a cut is legal iff `balance[i] == 0`. Covers both API shapes (OpenAI `tool_calls` + `role:"tool"`, Anthropic `tool_use`/`tool_result` blocks).
- `_tail_start` was replaced by `_tail_target` (pure size walk) + `_pairing_cut` (legalization). Preference: target if balanced → **backward** to the cut opening the group the walk landed inside (keeps the freshest call/result pair in the preserved tail; overshoot bounded by that one group) → forward past the group (only when backward would leave nothing to summarize) → shape fallback (never start the tail on a tool-result) for malformed transcripts with no balanced cut, instead of DSH's throw. The head cut is snapped forward the same way (`_snap_forward`). **Why backward matters**: the old always-forward advance could push the cut past every result and leave an EMPTY tail — the whole recent conversation became a summary (reproduced: 6 huge steps → `[system, human, summary]`; now the last step survives).
- `SessionLog.surface_generation` = count of surface mutations (appends + replace ops, bumped in `_apply_surface`, replayed identically by `from_events`). Mirrors DSH `surface.replaceGeneration`. It is the staleness token for async work prepared against the surface.
- `AgentLoop._compact_step` (extracted from `_run_loop`, which now just calls it) captures `surface_generation` BEFORE `compact()` and re-checks it before `_log_compaction`. On a mismatch it re-derives the input from the CURRENT surface (`_conversation_from_log` = `[messages[0]] + log.derive_messages()`, the system message is never on the surface) and recomputes, at most `MAX_COMPACTION_RECOMPUTES = 1`; a surface that keeps moving leaves the step uncompacted (did=False → the caller still adopts the re-derived list) and counts a `_compaction_stale_retries`, reported as `turn/end.reason.compaction = {stale_retries: N}`. Verified value: without the guard a message appended while the summarizer ran is logged on the surface but missing from the request — the "model-visible ⟺ logged" invariant breaks.
- Tests: `tests/core/test_context.py` (+10: balance shapes, snap back/forward, malformed fallback, a parametrized output-is-balanced matrix, freshest-step-in-tail) and new `tests/core/test_compaction_guard.py` (7: generation counter unit + recompute/give-up/per-turn-reset with a provider that mutates the log mid-summarize). Full suite: 756 passed, 1 failed = the known env artifact `tests/tools/test_sandbox.py::test_bashtool_surfaces_denial_hint_on_access_denied`.
